## 本轮结论

发现并修复一项本机实现缺口：用户停用时，授权清理曾依赖公司开户开关，且未删除 Plane 会话及待兑换 OIDC 授权码。原计划明确要求停用立即撤销平台会话和授权。新增三项用例先失败，修复后通过；重新启用用户不会恢复旧会话、OAuth/PAT 或待兑换授权码，其他用户不受影响。

实现提交 `77476caf7a`。API、worker、beat 与专用 company-provisioner 统一运行 `plane-custom/plane-backend:lifecycle-77476caf7a`，Gateway 保持 `ts-bdde88a622`。没有新迁移、仓库写入、自动归档或公网访问变更。公司管理员凭据仍只在专用开通过程中。

当前已完成本机可执行的实现与自动验收；进入人工验收，不等于整体生产签收。以下外部条件和运维确认不得标为通过。

## 剩余条件，不能用模拟通过代替

1. 第二个独立 GitLab 实例及两名授权测试用户；在同一 Plane 项目同时配置 GitHub 和两个 GitLab。灾备克隆不冒充独立客户实例。
2. 私有 GitHub 仓库与相应两用户 HTTPS Token，检查允许与拒绝。
3. 当前网络限制下远程 ChatGPT 的真实可达性及其实际支持的 OAuth/PAT 方式。不开放公网或建立隧道绕过限制。
4. 实际组织试点名单、项目和运营签收。证书、备份取回和正式切换条件由部署环境确认。
5. GitLab `blocked` 后旧会话无法访问已有实测；这不是物理删除所有存量会话的证据。当前开户进程只用官方用户管理 API，未接入 Rails 会话删除权限。官方提供的管理员 Rails 会话清理流程属于运维确认项，不能把它写成已自动化完成：[GitLab active sessions](https://docs.gitlab.com/user/profile/active_sessions/)。不为此给 Plane Web/Gateway 增加管理权限。
