# Plane 原生 API 与 MCP 能力对齐方案

2026-11-14 后续实施：用户已确认按 A/B 推进。共同授权、业务配额和工作项完整操作的实现与验证说明见 [原生 API/MCP 对等交付](native-api-parity.md)。下文差距表保留原规划基线；仓库工具已由后续仓库交付实现，本次继续保留。

核对基线：`c447ed657c`，2026-11-14。本轮交付为个人访问令牌页面修复和本方案；以下新增工具及鉴权调整尚未实施。
需求来源：用户要求“同一个用户、同一套授权，不要因为是 AI 调用就额外限制”；用途由令牌名称区分，不新增 AI/人工令牌类型。

## 统一规则

1. 只有一种个人访问令牌，沿用原生名称、描述、有效期、删除与最近使用记录。用户可命名为 Codex、报表、脚本等；名称不改变权限。
2. 对同一用户、同一授权、同一操作与资源，API 和 MCP 必须得到相同许可结果、字段校验、默认值和持久化副作用。权限由当前成员关系/角色决定，不检查调用方是否为 AI。
3. OAuth 是连接授权方式。现有明确缩小范围的 OAuth 或历史 sgp\_ 授权不能静默扩大；新增能力使用统一操作范围并重新取得相应授权。原生全权限个人令牌无需为每个新工具换一枚令牌。
4. 工具未封装应报告“功能未提供”，不可伪装成权限不足。所有者权限、隐私字段、账户停用、撤销规则对所有客户端一致。
5. 工具应暴露明确业务操作和结构化参数，不要求模型提供令牌、任意 URL 或用户 ID 来冒充操作者。Gateway 不连接数据库，使用独立短期委托调用 Plane 业务服务。

## 已存在的行为差异（不能仅靠新增工具解决）

- **字段与默认值**：`singularity/api.py:Items.post` 只写 name/description_html，创建要求配置“待整理”或 initial_state_id，默认分配人为 None，类型通过标签映射；原生 IssueSerializer 支持更多字段并使用原生默认规则。通用 create/update 工具必须与原生一致，不能强制这些讨论归档规则。
- **流程**：save_discussion_result 使用 prepare/decision_id/commit。这是“准备后归档”的业务语义，可保留为便捷工具；不能要求所有原生 CRUD 都额外经过一轮 AI 专用审批。客户端已有执行审批与服务端业务权限是不同层次。
- **鉴权结构**：原生 API 使用 ProjectEntityPermission 等类；扩展接口使用 visible_projects、readable_items 与 allow_permission。部分逻辑虽然相似，仍需逐操作角色矩阵验证，不能凭复用用户 UUID 就宣称全量等价。收敛到共同业务权限入口，避免复制角色表。
- **限流**：原生 ApiKeyRateThrottle 使用配置 API_KEY_RATE_LIMIT（源码默认 60/minute），以令牌计数；扩展接口按用户 60/min，并另有按用户/项目写入 15/min。应统一相同操作的配额和计数主体；不得仅因经过 MCP 增加写入限制。认证交换开销不应被当作额外业务写操作。
- **内容和字段表示**：归档正文限制 50,000 字符，并以 Markdown 转换 HTML；原生 API 接受自己的表示及验证。通用操作应服从共享字段规范与容量限制，不以 AI 身份额外截断。保留归档的 Markdown 便利转换，但不能悄悄丢字段。
- **OAuth 操作范围**：目前只有 projects:read、workitems:read、workitems:write、capabilities:read，无法表达后续成员、周期等完整能力。需统一操作注册表供 API 与 MCP 检查，原生 PAT 表示用户现有权限；OAuth 可显式授予其中一部分，历史授权不自动扩权。
- **幂等与版本**：当前讨论保存已有来源唯一键/事务和版本冲突保护，原生 PATCH 已有公共行锁。通用操作将幂等键、条件更新下沉到可供所有客户端使用的共同服务，覆盖网页/API/MCP 竞争，而不是去掉保护来追求表面一致。
- **仓库**：当前页面会话可调用不等于 PAT 已可调用。应补齐授权适配，保持“Plane 项目权限 + 本人上游凭证”的双重检查；这与调用方是人还是 AI 无关。Git 写入/PR/MR 本身没有在当前服务实现，不能作为简单封装声称已支持。

## 建议实施顺序与验收单元

| 阶段                  | 实施内容                                                                                                           | 结束条件                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| A：共同授权和业务入口 | 建立已注册 operationId → 原生服务/序列化器/权限映射；支持绑定原生令牌的短期委托；合并配额策略，列清 OAuth 范围迁移 | 同用户同令牌跨两种传输的权限矩阵一致，撤销立即生效，历史 OAuth 不扩权；明确字段与默认值契约       |
| B：工作项完整闭环     | 当前用户、项目详情、元数据读取、完整查询、通用工作项创建/更新/删除；保留讨论归档便捷工具                           | 可真实修改状态、负责人、标签、优先级和日期；原生默认规则一致；幂等重试及网页并发不丢修改          |
| C：协作与计划         | 评论、链接、关系、活动、周期、模块、收件箱                                                                         | 每个已注册操作都有工具覆盖及等价测试；不能写的活动在两端均不可写                                  |
| D：项目与管理         | 项目生命周期、状态/标签管理、项目成员、邀请、便签                                                                  | 管理员/成员/访客/所有者同条件同结果；删除与通知副作用真实验收                                     |
| E：文件和仓库         | 资产/附件上传下载及关联、仓库扩展接口 PAT 授权、仓库目录/文本读取                                                  | 正确处理二进制/大小限制、commit SHA、凭证归属、上游拒绝；同一公开 API 操作不因 MCP 身份受额外限制 |

实现方式优先采用有明确 Schema 的业务工具，复用原生业务服务。可从已注册 API/OpenAPI 生成工具候选和覆盖报告，但不能自动把登录回调、管理员密钥或任意 HTTP 转发暴露为工具。此边界是服务契约，不是 AI 专属权限。新的业务操作仍需独立实现和验收，本轮不自动执行以上阶段。

## 可复现的对等验收

- 使用两名不同角色的测试用户，各自使用同一原生 PAT 分别调用原生 API 与 MCP；比较状态码的业务含义、可见集合、分页、字段与落库结果，不只比较 HTTP 200。
- 覆盖管理员、成员、受限访客、移除成员、非成员；同一资源上的读、写、删、管理操作许可一致。审计主体相同，不允许模型传 user_id 改变操作者。
- 删除/过期/停用令牌后，原生请求和已经交换出的短期凭证均拒绝；跨用户凭证或 decision_id 引用被拒绝。
- 同样的合法字段、默认负责人/初始状态在两端一致；非法跨项目标签、负责人、状态在两端均失败。只提供的字段才能更新。
- 响应丢失后相同幂等键只产生一次变更；使用旧版本更新应返回冲突，并验证网页和原生 API 同时编辑的场景。
- 配额采用同一策略：同一操作不因 MCP 额外限流；测试分别核对业务请求和认证交换计数。
- OAuth 仅允许已明确授予的操作，新增工具不能绕过 scope；名称叫“Codex”或“报表”的原生令牌在同条件下权限完全一致。
- 工具必须返回真实结果、来源及错误；未实现的工具明确标为缺口，不以模拟成功替代真实验收。外部 GitLab/GitHub 条件不足的项单列。

## 本轮页面验收

顶部固定一个“创建个人访问令牌”入口，空列表、已有令牌、搜索无结果和删除后的状态保持一致；弹窗仍使用名称和描述，不引入用途类型或 AI 权限开关。中英文名称与创建/删除/一次性显示说明一致。页面修改不改变令牌或 OAuth 的实际授权行为。
