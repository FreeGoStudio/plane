# 平台文档仓库执行身份

需求依据：2026-11-25 用户要求改进文档审查的平台覆盖能力，解决 SING-19 提交
`715a937e72c13325c5206e23216f0e4c18d005f3` 因复用仓库 22 的项目令牌而持续排队的问题。

## 行为

- 公司账号维护进程自动扫描已绑定、已启用的公司 GitLab 文档仓库，已有和新增仓库使用同一流程。
- 每个仓库独立签发项目级 `api` / `write_repository`、Maintainer 执行令牌。管理员身份只参与签发，
  不交给审查执行器。个人 PAT 功能开关不影响平台执行身份维护。
- 令牌通过现有 keyring 加密存储，密文绑定平台仓库、GitLab 实例和外部项目编号；MR 操作按仓库取用。
- 定期检查有效期，尊重实例有效期上限；先持久化经验证的新令牌再撤销旧令牌。
  持久化签发名称用于回收响应丢失时创建的孤立令牌。进行中的已授权合并暂缓正常续期。
- 一个仓库接入失败不阻止其他仓库接入。非公司托管实例明确报错，不向其他 GitLab 主机发送公司凭据。
- 已登记的旧仓库在新凭据验证完成前保留原执行令牌兼容路径；新增仓库不回退到该令牌。
- MR 准备有独立次数：权限、资源不可见、输入冲突等明确失败结束排队；暂态错误最多尝试五次。
  失败记录沿用原有重试接口，不消耗 AI 执行次数，不篡改旧记录。
- 合并门禁接受目标仓库自己的执行身份，仍要求精确 SHA、已有采用授权及完整原有校验。
  本次不自动批准或合并文档，也不移除服务端 hook 安装与验证要求。

## 部署与恢复条件

本文件不是部署成功记录。需先备份配置及数据库，再应用 `db.0146_document_repository_executors`，
同步更新 API、document-review-worker、document-adoption-worker、company-provisioner。
新版本沿用现有公司管理员维护入口及 vault keyring，无需将管理员令牌挂到其他服务。
保留旧 keyring 版本以读取尚未重新加密的密文。

部署后先核验绑定仓库的 `DocumentRepositoryExecutor.status=ready`，再通过正常业务接口恢复失败审查。
已有 queued 记录由原准备循环继续执行；已变更输入的旧记录应按原规则失败，不强行恢复。
不得把 AI 完成、AI 通过和人工采用混为同一验收结果。

新的文档仓库可以完成审查和 MR 准备；正式采用仍需要该仓库已有的服务端 gate 安装、登记和验证。
外部 GitLab 的管理员授权与服务端 hook 自动部署不是本次变更内容。

回退应用版本时保留新增表和字段及审计记录，不反向覆盖业务数据库；旧项目令牌不在本次自动维护中撤销。
