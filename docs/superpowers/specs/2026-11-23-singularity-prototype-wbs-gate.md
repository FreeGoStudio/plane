# Singularity 操作统一与原型确认门禁

日期：2026-11-23。状态：用户已确认业务规则；本文件为待审阅的具体设计，尚未实施。

## 原始要求

用户先指出：PRD 经平台 Review 后已经可以进行任务拆分，但原型尚未生成；采用版本、WBS 等操作需要在 ChatGPT 客户端与 Plane 之间切换。

用户随后明确确认：

> 涉及界面的需求必须先确认原型才能拆分，不涉及界面的可以跳过。把这些操作统一到 Singularity Plugin 中触发，Plane 和插件都遵守同一套规则。

以上原话是需求依据。下列字段、接口组织和校验时机是实现设计，不扩展业务需求。

## 已有能力与直接缺口

- Plane `apps/api/plane/singularity/wbs.py` 的页面与 MCP 共用 `start_run`、`review_run`；已有版本检查、幂等和批准后创建子任务。应保留。
- `source_snapshot` 当前保存需求正文、更新时间和已有子任务，没有采用的文档 SHA、原型确认或界面影响字段。`start_run` 没有原型门禁，`review_run` 也不核对原型版本。因此两个时机都需补齐校验。
- 插件已可发现 `adopt_requirement_revision`、`start_wbs`、`get_wbs`、`review_wbs`，应复用，不能在客户端重建生成器或任务创建流程。
- 文档采用记录已有 `RequirementAdoption`，保存操作者、源 SHA、合并 SHA、类型及执行结果；采用进行中不能视为采用完成。
- 原型服务 `platform/server/plane-workflow.mjs` 已保存候选、固定包、PRD 引用、人工评审和快照。`approved` 与 `delivered` 有明确区别。已有人工确认不应重做，原型确认不要求额外发布。
- 原型服务当前通过 Plane 评论核验评审人，`plane-identity.mjs` 只信任服务端核验过的身份。插件不能直接传入 `kind=human` 冒充人工，也不能仅上传一个“已确认”布尔值放行 WBS。
- 插件当前 PRD 技能将原型按等级按需提供。用户本次规则优先：涉及界面时，无论 L1/L2/L3，拆分前均需有效原型确认；非界面需求不强制补做原型。

本轮证据来自源码与当前会话工具定义，未验证部署镜像或真实业务流程。

## 采用的方案与取舍

采用用户已明确选择的方向：插件与 Plane 共用服务端业务动作和规则，原型服务继续提供固定候选及执行证据。

仅调整插件提示词无法约束 Plane 按钮和直接 API；仅隐藏按钮也不能防止旧草稿批准。两种方案均不满足要求，不作为替代实施。

## 目标行为

1. Plane 保存需求是否涉及界面，建议字段为 `ui_impact`：`unknown`、`required`、`none`。分类绑定当前需求依据及操作者。插件可依据明确需求提出分类并提交；不把无法判断默认为非界面。
2. 涉及界面：采用固定需求版本后制作原型；用户查看固定候选并明确确认；服务端保存绑定同一需求与文档版本的有效确认，随后才允许生成 WBS。
3. 不涉及界面：明确记录 `none`，跳过原型步骤；仍遵循适用于该需求的既有材料和版本规则。不为轻量非界面需求强制创建 PRD 仓库。
4. 未明确界面影响：返回具体待确认项；用户可以在任一入口补充，不要求先生成原型才允许登记为非界面。
5. WBS 生成仍在平台 AI/Worker 执行。生成草稿不创建子任务；用户明确批准该份草稿后，才由已有事务创建子任务。
6. 在生成及批准两个时机执行同一规则检查。需求依据、采用 SHA 或对应原型候选已变化时，旧确认不能放行新输入；旧草稿保留历史，并指出需重新确认或生成的原因。
7. 既有已完成任务和历史决定不删除、不自动撤销，不批量补造历史原型确认。历史待批准草稿须在本次批准时符合现行条件。

## 服务端证据与身份

Plane 负责需求分类、业务决定及 WBS 放行判断；原型服务负责候选、构建包和执行证据。建立最小必要的受信证据查询/登记契约，不复制第二套原型执行流程。

原型确认至少关联：Plane 项目与需求 ID、需求依据版本、已采用文档 SHA（有版本化文档时）、候选 ID/提交、构建 ID/摘要、评审 ID/版本、真实操作者及确认时间。服务端核对候选属于本需求、包可验证、前置自动验证满足原有规则，且未失效或被驳回。

页面登录身份与 MCP 委托身份进入同一业务服务。客户端明确提交确认对象；服务端验证权限、对象版本并记录决定。对话中的一般“继续”不自动等同于批准未展示的原型或 WBS 草稿。复用已有幂等机制处理重试及响应丢失。

已有合法原型确认通过服务端读回复用；不能要求用户仅因切换入口而重复确认。原型服务不可达或证据暂不可读时，界面需求报告待验证，不伪造通过，也不要求非界面需求连接原型服务。

## 插件与页面

插件支持连续执行：查询 Review → 采用审查通过版本并等待完成 → 生成/展示原型 → 提交明确的原型确认 → 发起 WBS → 展示草稿 → 提交明确批准/驳回。非界面需求跳过原型链路。

新增的分类、原型状态与确认能力通过业务 MCP 暴露；工具名称以实施时 Schema 为准。复用现有 WBS 工具，不改为插件本地拆分。页面读取同一门禁状态，展示缺项和固定原型入口，并允许提交相同决定。

审查未通过时的“人工确认采用”是现有特殊权限动作，本轮不将普通“采用此版本”解释为自动豁免。现有页面专属限制保持；如要将此特殊动作也迁到插件，应单独明确权限与人工授权契约。

## 实施归属

- `D:/plane-source`：需求门禁记录及迁移、共享校验、WBS 快照与批准复验、业务接口、Gateway 工具、原有 WBS/Review 面板和翻译、契约测试。
- `D:/workspace/ai-native-workbench`：复用已有确认/固定包能力，增加与 Plane 之间必要的受信证据及确认适配；不新增通用管理页面，不继续扩建历史 WBS 实现。
- `D:/workspace/Singularity-Plugin`：更新需求阶段的操作引导、等级规则、确认与 WBS 交接说明及必要工具适配；按既有约定递增双插件/共享运行时版本，完整安装并核验。
- 运行部署副本不作为开发目录；实际部署前重新读取本机维护信息及核对运行版本。部署后更新维护记录，源码完成与部署验收分别报告。

## 验收用例

| 场景                                           | 预期                                             |
| ---------------------------------------------- | ------------------------------------------------ |
| 界面需求仅 PRD Review 通过，原型未生成         | 页面和 MCP 均拒绝生成 WBS，返回原型缺项          |
| 原型已生成/自动验证通过，尚未人工确认          | 两个入口均不能放行                               |
| 固定原型已由授权用户确认，匹配当前需求依据     | 两个入口都能生成草稿，无需先发布原型             |
| 非界面需求，无原型或原型服务不可达             | 不因缺原型阻断，既有其他条件继续适用             |
| 界面影响未知                                   | 返回待分类原因，可在任一入口完成分类             |
| PRD/原型版本变化，沿用旧确认或旧 WBS 草稿      | 生成/批准拒绝不匹配版本，保留旧证据              |
| 确认对象属于其他项目/需求，或操作者无权限      | 拒绝决定及放行，不产生子任务                     |
| 重复提交确认/批准，或响应丢失后重试            | 返回既有决定/任务，不重复创建                    |
| 插件确认原型后进入 Plane；Plane 确认后进入插件 | 同一状态、版本和权限结果，无重复确认             |
| 明确批准准确 WBS 草稿                          | 仅按现有事务创建任务，自动测试成功不代替人工批准 |

## 范围及完成标准

不扩展全面业务代码扫描、不替换 Hatchet、不改公网限制、不自动批准真实业务原型或任务、不自动发布业务系统。原型证据适配是满足本次规则的直接依赖，其余关联缺口只登记。

完成需分别具备：实现及本地提交、适用自动测试通过、隔离环境双入口端到端验收、插件完整安装核验。真实用户对业务原型的确认仍由用户完成，不以测试夹具代签。
